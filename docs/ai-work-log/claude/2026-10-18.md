## 1. B2a: intermittent evidence AccessDenied — recover lookups, diagnose citations

**Requested by:** Jayanth (Part B) · **Area:** Claude (backend) · **Branch:** `Jk`

### Root cause
`agents/loop.py` executed read tools without error handling. When the model asked `fetch_evidence`,
`get_order` or `trace_dependencies` for an ID that is missing (e.g. `HB-O201` before it existed, or any
guessed ID), `AccessDenied` propagated and the whole run ended `blocked: planning: AccessDenied`.

### What changed (access checks unchanged)
- Loop: `AccessDenied`/`LookupError` from a read tool → tool result
  `{status: "unavailable", requested: [safe ids], note: "...Do not cite it."}`. Same answer for missing and
  forbidden (no existence leak); warning log `agent_tool_unavailable tool=… ids=…` (record-ID charset only).
- Engine: platform evidence failures raise `EvidenceUnavailable(LookupError)` with a sanitized ID; a plan that
  *cites* an unavailable ID still blocks, now as `planning: evidence_unavailable (<id>)`.
- `presentation.conversation_reply` treats both error forms as "evidence unavailable".
- Harbor: `HB-O201` added as a versioned Order record; order evidence shows the "no installation trace"
  warning only where assembly traces exist.

### Verification
- `test_evidence_recovery.py` 3/3 (scripted). Full live suite **221 passed**.
- **Real Gemini, Harbor pause → port closure → resume through the authenticated API: 2/2 completed, Reviewer
  accepted** (r2 covers hb-task-book-route-a and hb-task-confirm-friday). Before the fix the same path blocked
  with AccessDenied twice.

- Endpoints: `GET /workflow/capabilities` → {plan_review:true, work_setup:false, reminders:false};
  `GET|POST /sessions/{sid}/runs/{rid}/plan-review`; `GET /plan-reviews`; `GET /approvals` (plan reviews + this
  user's decided actions; never seeded decisions).

## 6. B4: durable reminders with a real worker (in-app delivery)

**Requested by:** Jayanth (Part B) · **Area:** backend · **Branch:** `feat/b4-reminders`

### Built
- `workflow/reminders.py`: occurrences in the item's IANA timezone (daily / milestones / custom; past times
  skipped; DST-correct), one `Reminder` per occurrence with unique `delivery_key`; scheduled on confirm, stopped on
  complete/cancel (work-setup hook), rescheduled via `work_setup.update_reminder` (confirmed items).
- Worker `run_once`: claim with lease (one conditional query) → re-check item is confirmed → write the chat message
  (deterministic id + content, so a retry can't duplicate) → `ReminderDelivery` + delivered. Failures: attempts +
  exponential backoff, `failed` after 5 with the error class. Heartbeat key (120 s TTL) drives the `reminders`
  capability flag, so the UI never sees reminders "available" without a running worker.
- `scripts/reminder_worker.py` (loop or `--once`); optional in-process worker `RELAYMIND_REMINDER_WORKER=1`.
- API: `GET /reminders`, `GET|POST /work-items/{id}/reminders`, `POST /reminders/{id}/snooze`; ReminderConflict → 409.
- Constraints: Reminder.id, Reminder.delivery_key, ReminderDelivery.id. `docs/workflow-api.md` for Codex.

### Problems
- A multi-file heredoc edit failed in Git Bash (quoting) and applied nothing; redone with a Python patch file.

### Verification
- `test_reminders.py` 4/4 (IST conversion, London DST, milestones dedupe, bounds); `test_reminders_real_db.py` 5/5
  (idempotent scheduling, delivery, rerun / fresh-client dedupe, 4 concurrent workers → 1 delivery, crash after the
